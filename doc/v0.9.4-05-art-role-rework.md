# v0.9.4-05 · 角色画像与 mascot 重做（增量）

> 本文是 [v0.9.4-04-art-assets.md](./v0.9.4-04-art-assets.md) 的增量修正（不升版本号）。
> v0.9.4-04 把 23 张 png-art 资源接入界面后，人眼复核发现 `role` 组存在观感缺陷，
> 本次只重做 **3 张角色画像 + 1 张 mascot**，其余 19 张不动。
> 交付日期：2026-09-22。

## 一、问题与成因（先定性，再动手）

v0.9.4-04 §五 已把 `role-*` 列为「只能人工判断」的风险项，本次复核确认该风险成立，且成因有两个叠加项：

| # | 现象 | 成因（实测） |
| --- | --- | --- |
| 1 | 44px 渲染框里人像极小、五官糊成一团 | `LoginScreen.tsx:331` 用 `h-11 w-11`（44px）`object-contain` 承载；而角色源图内容仅 ~343×316px 居中于 512²（占 67%），可见尺寸 ≈28px。**根因**：`trim.fit_to_target` 明确不上采样，而 v0.9.4-04 出图时采用「三张并排单趟生成后切分」以保风格一致，切出的单张只有 ~343px 宽 |
| 2 | 「脸色不对」——浅奶油肤色在页面里发灰发脏 | 角色卡选中态底色是 `mint-soft #E8FAF8` / `primary-soft #EEF2FF` / `coral-soft #FFF1F1`（`LoginScreen.tsx:14-18`），未选中态是 `surface`。**浅奶油肤色（≈`#F2E3CE`）与这些浅底几乎没有明度差**，在 28px 尺度下不成形 |
| 3 | mascot 观感杂乱 | 出图含腹部齿轮、胸口装饰等多处细节，在 `h-24 w-24`（96px）下杂糅；且与品牌无关联 |

**量化锚点**：`role-*` 主体占画布 66~68% 宽 → 44px 框内可见 ≈28px；而卡片插画占 55~84% → 同框内可见 ≈37px。
两者相差近一倍，这正是 v0.9.4-04 §五 追问的「是否显得比卡片插画『轻』」。

## 二、设计决策（本批定调）

| 决策点 | 选定 | 理由 |
| --- | --- | --- |
| 角色配色 | **纯 token 单色人像** | 脸用 `surface #FFFFFF`、五官用 `ink #26221D` 点/线、身体与肩侧小图标用 accent 色块。**零新增 token**，与卡片插画（同为「token 色 + 扁平几何」）风格完全同族；彻底消除肤色这一色板外的变量 |
| mascot | **纸感书本精灵** | 呼应产品「暖纸感 + 教育」调性；书本/纸页是教育语义的天然载体，且比机器人的机械细节更少、更纯形 |
| 尺寸 | **允许 ≤1.35× 轻放大，主体基本填满画布** | 源为扁平矢量插画（非照片），1.25~1.35× LANCZOS 放大在视觉上几乎无损，却能把 44px 框内可见尺寸从 ≈28px 提到 ≈40px |

**不可动摇的约束**：`src/theme/art.ts:9-12` 以**精确路径**静态 import 四张角色图，本次**不得改名、不得换目录**，只替换同名文件内容。

**自动可验**

1. `python scripts/png-art/run.py --verify-only` —— 23 张全部通过 6 项断言（Windows GBK 控制台需 `PYTHONIOENCODING=utf-8`）。
2. `python scripts/png-art/run.py --list` —— 23 条全完成。
3. `npx tsc -b` —— `src/theme/art.ts` 的精确路径 import 仍成立（四张文件名未变）。
4. `npx vitest run` —— `src/__tests__/art.test.ts` 全绿（角色口径差断言 `schoolAdmin→role-admin`、`bureau→role-district` 依赖文件名，本次不变）。
5. `npm run build && npm run check:budget` —— 120 / 297KB 门禁仍绿。**图片不进 `budget.mjs` 口径**，故预期无寄存器变化；若包体因四张图体积变动而漂移，属于 `dist` 体量而非 JS 门禁。
6. `npx playwright test e2e/critical-path.spec.ts e2e/loom.spec.ts` —— 硬门禁全绿（⑧ 断言 4 张 `public/` 图标可达；角色图走 `dist/assets/` 哈希通道，不受影响）。
7. 视觉基线：`npx playwright test e2e/visual.spec.ts --update-snapshots=all` 后不带 flag 复核无差异。
   **必须显式带 `=all`** —— 详见 v0.9.4-04 §五-7 记录的「小面积改动 + 默认 `changed` 模式会静默不落盘」踩坑。

**只能人工判断（显式声明）**

- `verify.py` 的 6 项断言只覆盖 RGBA 模式、透明角、半透明 AA、覆盖率区间、无 1px 不透明环、体积上限；**「脸色是否协调」「人像在 44px 下是否可辨」「mascot 是否可爱」无法自动断言**。
- 本批必须人眼看两件事：
  1. 四张图叠在 `#FAF8F5` 与深色底上各看一次（生成器 README 要求）；
  2. **按真实渲染尺寸看**——角色在 44px、mascot 在 96px 下截图确认，而不是只看 512px 大图。这是本次问题被发现的方式，也是唯一能确认修复的方式。

## 六、风险与对策

| 风险 | 对策 |
| --- | --- |
| 限幅放大后画面发虚 | 限幅 1.35×，且源为扁平矢量；放大后仍走 `verify` 的半透明 AA 断言（`semiMin` 30）兜底，明显发虚会体现为 AA 像素异常 |
| 单色人像「白脸」在浅色卡片上反而更糊 | 白脸靠 `ink` 五官与 accent 身体提供轮廓；实测 44px 截图确认。若仍偏弱，退路是把面部轮廓改为 `line` / `ink-mute` 描边（仍在 token 内） |
| 单趟并排生成再次切出过小内容 | 限幅放大已覆盖 1.25× 情形；若切出内容小于内区的 1/1.35 则 `trim` 仍报错，届时重出图 |
| 四张图体积变化冲击 `dist` 体量 | 图片不进 JS 预算口径；逐张仍有 400 / 900KB 断言 |
| 改提示词误伤其他 19 张 | 本次只动 manifest 的四条；其余 `prompt` 与 `out` 不变，`--verify-only` 会对全部 23 张复核 |
| 视觉基线静默不更新 | 显式 `--update-snapshots=all` 并复核 mtime / `git status`（v0.9.4-04 踩坑记录） |
