

# EDUStudio v0.9.4

## 版本主题

**v0.9.4 · Loom 空间任务台：把简报任务摊开来工作**

建议 README 里的版本描述写成：

> `v0.9.4 · 空间任务台 · 简报任务平铺 · 拖拽编排 · 可视依赖 · 人机协同`

这一版不建议定位成“流程图编辑器”。

产品语言应该是：

**空间任务台 / 任务画布 / 摊开处理**

而不是：

**Workflow Editor / DAG / Node Graph**

这符合 v0.9.2 已经确定的“把工程师语言换成教育者语言”的方向。当前 AgentTrace 本身就已经刻意把 Tool Call / JSON 转成教育者可理解的业务文案。

# 二、最重要的数据关系：不要推翻“一卡一任务”

这是 v0.9.4 最核心的设计决策。

不要变成：

```text
BriefingCard
    ↓
Loom Node
    ↓
新的 Workflow
    ↓
新的 Session
```

而应该：

```text
BriefingCard
     │
     │ cardId
     ▼
Loom Task Node
     │
     │ sessionId
     ▼
ChatSession
     │
     ├──── AgentTrace
     │
     └──── Artifact
```

也就是说：

### **Loom 是现有任务系统的空间视图，而不是另一套任务系统。**

当前 `ChatSession` 已经有：

```ts
interface ChatSession {
  id: string
  title: string
  role: RoleId
  entries: ChatEntry[]
  createdAt: number
  updatedAt: number
  cardId?: string
}
```

而且 `ensureCardSession()` 已经确保简报卡与会话幂等绑定。

所以 v0.9.4 不要破坏它。

# 四、一张简报卡进入 Loom 后发生什么

例如教师今日简报有：

```text
① 高一三班函数薄弱点分析
② 为薄弱学生生成分层练习
③ 完善家长会发言稿
④ 整理本周教学总结
```

用户采纳 ①、②、③。

当前 v0.9.3 是：

```text
左侧任务

函数薄弱点分析
分层练习
家长会发言稿
```

v0.9.4 同时生成：

```text
空间任务台

┌──────────────┐
│ 函数薄弱点分析 │
│ 来自今日简报   │
└──────────────┘

┌──────────────┐
│ 分层练习       │
│ 来自今日简报   │
└──────────────┘

┌──────────────┐
│ 家长会发言稿   │
│ 来自今日简报   │
└──────────────┘
```

默认不要替用户连线。

因为：

> **空间关系必须是用户意图，而不是系统猜测。**

但可以提供：

`✨ AI 建议整理`

比如建议：

```text
函数薄弱点分析
       ↓
生成分层练习
       ↓
生成教学总结
```

用户确认以后才真正创建 edge。

# 五、节点类型设计

v0.9.4 我建议只做 **5 个正式节点 + 1 个轻量节点**。

| 节点      | 用途          | 对应 EDUStudio               |
| ------- | ----------- | -------------------------- |
| 📌 任务   | 简报采纳任务      | BriefingCard + ChatSession |
| ✨ AI 模块 | 自定义一段 AI 工作 | goal/instruction           |
| 🔧 工具   | 指定业务工具      | ToolRegistry               |
| 📄 文档   | 关联产出        | ArtifactDoc                |
| ✋ 人工确认  | 需要人审批后继续    | checkpoint                 |
| 📝 便签   | 自由记录        | note                       |

这里尤其推荐 **人工确认节点**。

它会让 EDUStudio 的教育应用属性明显高于普通 Agent Canvas：

```text
成绩数据
   ↓
AI归因分析
   ↓
✋ 教师确认
   ↓
生成分层作业
```

这正好符合 EDUStudio 已经强调的：

> AI 生成内容仅供参考，采纳前人工复核。

# 六、节点卡片怎么设计

不要使用你 HTML 原型里的深色背景。

EDUStudio 当前设计 token 是典型浅色纸感：

* `bg`: #FAF8F5
* `surface`: 白
* `surface-2`: 暖灰
* primary: 靛蓝
* coral
* amber
* mint

现有 token 就应该直接复用。

例如：

### 普通任务

```text
┌─────────────────────┐

│ 找出主要失分原因     │
│                     │
│ ○ 待处理             │
└─────────────────────┘
```

白色卡片：

```text
bg-surface
border-line
rounded-2xl
shadow-soft
```

---

### 执行中

```text
╔═════════════════════╗
║ ✦ AI 正在处理       ║
║                     ║
║ 生成分层练习         ║
║                     ║
║ 第 2 / 4 步          ║
╚═════════════════════╝
```

使用：

```text

```

节点右上角呼吸点直接复用 v0.9.3 的生成中视觉语言。

# 七、画布交互

这里基本可以继承你提供 HTML 的 Loom 思路。

## 1. 拖拽节点

Pointer Events：

```text
pointerdown
   ↓
capture pointer
   ↓
pointermove
   ↓
update local position
   ↓
requestAnimationFrame
   ↓
redraw SVG
   ↓
pointerup
   ↓
persist
```

但有个重要优化：

**不要 pointermove 每次都写 Zustand + LocalStorage。**

v0.9.3 才刚刚解决高频持久化问题。项目路线图已经明确记录过拖动/输入逐次写盘会造成卡顿。([GitHub][2])

建议：

```text
拖动过程
→ component local state / transient position

pointerup
→ loomStore.moveNode()

300ms debounce
→ LocalStorage
```

# 十、连线不能只是装饰

这是我认为 v0.9.4 最需要避免的问题。

如果：

```text
A → B
```

只是画了一根线，但是系统还是独立执行 A、B，那么 Loom 很快就会沦为“漂亮流程图”。

所以规定：

### Edge = dependency

```text
A → B
```

意味着：

```text
B.inputs += A.output
B.dependsOn += A
```

运行条件：

```ts
canRun(B) =
  every(parent.status === 'done')
```

从而：

```text
分析学情
   ↓
生成习题
```

实际执行 B 时，输入应该变成：

```text
目标：
生成针对性练习

上游任务结果：
[分析学情节点输出]
...
```

这才是真正的 Loom。

这里建议做一个很克制的改造。



```ts

```

这样旧逻辑：

```text

```

Loom 执行时只是多注入：

```text

- 学情分析：函数概念失分率 31%
- 作业分析：第 4 题错误集中

当前目标：
生成一套分层练习
```

# 十二、运行方式

原型里有：

> “运行这张网”



EDUStudio 可以改成更自然的：

### `▶ 开始处理`

点击之后：

```text
Graph
 ↓
validate
 ↓
topological sort
 ↓
ready nodes
 ↓
execute node
 ↓
write ChatSession
 ↓
capture result
 ↓
unlock child nodes
 ↓
next
```

v0.9.4 **先不要做真正并发执行**。

虽然 AgentTrace 已有 parallel group，但 `chatStore` 当前仍然存在全局 `streaming` 单飞门控，因此直接同时执行多个 Loom Task 会引入明显状态竞争。

这一版：

**DAG 支持分叉，但执行器先串行拓扑运行。**

v0.10 再升级并行 scheduler。

# 十三、空间画布与 Agent Trace 的关系

这是可以做得非常漂亮的一块。

现在：

```text
Plan
Tool Call
Tool Result
Reflect
Done
```



v0.9.4：

点击一个 Task Node：

```text
┌─────────────────────┐
│ 高一三班薄弱点分析   │
└──────────┬──────────┘
           │ 展开
           ▼

  ① 查询学情
       ↓
  ② 查询作业
       ↓
  ③ 错题归因
       ↓
  ④ 生成分析报告
```

这里建议采用：

### **任务节点折叠 / 展开**

普通状态：

```text
[高一三班学情分析]
```

双击：

```text
        高一三班学情分析

  查询学情 ─┐
            ├→ 错题归因 → 报告
  查询作业 ─┘
```

这些子节点**不用独立持久化成业务任务**。

直接由现有 `AgentTraceEvent` 投影。

于是：

```text
plan
→ Plan nodes

tool_call
→ Tool node running

tool_result
→ Tool node done

artifact_meta
→ Artifact node

done
→ Task done
```

这会让 v0.9.3 的 Agent 可见化资产全部被复用。

# 十九、技术选型：我反而不建议 v0.9.4 上 React Flow

React Flow/XYFlow 本身很适合这件事，它原生就是做 node-based UI、交互图与 workflow 的。([GitHub][3])

但 **EDUStudio 当前阶段不适合引入它。**

原因很现实。

当前项目依赖只有：

```text
React
Zustand
Recharts
Lucide
clsx
tailwind-merge
```

([GitHub][4])

而且你的 CI 有非常明确的包体门禁：

```text
main gzip ≤ 120 KB
total JS gzip ≤ 285 KB
```

v0.9.3 已经实测约：

```text
277.1 KB
```

只剩约：

```text
7.9 KB
```

余量。

所以如果现在引入 XYFlow：

> 基本意味着必须重新提高 total budget。

这会破坏 EDUStudio 一直坚持的：

**轻量、纯前端、离线、零翻车。**

而你提供的 HTML 已经证明，当前需求完全可以由：

```text
PointerEvent
+
CSS transform
+
SVG
+
Zustand
```

解决。

### 所以 v0.9.4 建议继续“零新运行时依赖”。

等未来出现：

* 100+ 节点
* grouping
* nested workflow
* minimap
* advanced routing
* multi-selection
* 大型 DAG

再考虑 XYFlow。

# 我最推荐的 v0.9.4 功能边界

如果让我直接给这一版砍 scope，我会锁死在下面这条线上：

**必须做：**

`简报任务自动进入 Loom → 自由拖动 → 新增 AI/人工节点 → 自由连线 → 持久化 → 按依赖真实执行 → Agent Trace 动态亮起 → Artifact 自动出现`

**暂时不做：**

`多人协作 / 无限层级子流程 / Minimap / 复杂框选 / 100+节点 / 第三方节点插件 / 真正并行 DAG / 版本分支 / 云端同步`

这样 v0.9.4 会是一个**功能感非常强，但工程范围仍可控**的版本。

尤其我建议把这句话作为整个版本的产品原则：

> **简报负责发现“今天值得做什么”，Loom 负责决定“这些事应该怎么一起做”，Agent 负责真正把它们做完。**

这就把你现在的“**简报 → 工作台 → Agent → Artifact**”链路彻底串起来了，而不是在中栏凭空增加一个流程图玩具。
