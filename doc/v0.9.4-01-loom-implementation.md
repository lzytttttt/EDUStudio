## 二、P0 阻塞项：必须先定架构

### 决策 1 · LoomRunner 执行节点走 `sendMessage`，不走直调 `runTask`

**代码事实**：执行 Agent 的唯一生产入口是 `chatStore.sendMessage`（`chatStore.ts:159`），它持有：
- 全局单飞门控 `streaming`（`chatStore.ts:161`，`retry` 同样受 `:191` 约束）；
- `activeController` 模块级单实例（`chatStore.ts:75`）；
- Trace 写入、artifact 流缓冲（`:79-81`）、失败落盘（`entry.error`，`:296-310`）、会话持久化。

若 LoomRunner 直调 `getProviders().agent.runTask`，上述四项全部断链，需要各自重写一遍——与"克制改造 Harness"的初衷相悖。

**决策**：`runner.ts` 通过 `sendMessage` 执行节点，并在发起前检查单飞：

```text
canRun(node) = every(parent.status === 'done') && !chatStore.streaming
```

被占用时节点回 `queued` 等待（与 `focusStore.pump` 的"回队 + 退出避免忙等"同款策略，`focusStore.ts:68-74`）。

**副作用与对策**：`sendMessage` 会 `ensureCardSession` 并切换 `activeId`（中栏聊天会跳到该节点会话）。
对策：runner 在整批执行前记录 `activeId`，批次结束后恢复；执行中的节点状态通过画布高亮表达，不依赖聊天视图。

### 决策 2 · 上游输出的采集口径

**输入侧**：`AgentTaskInput` 无 `context` 字段（`types.ts:178-183`）。扩展为纯增量：

```ts
// types.ts
export interface AgentTaskInput {
  role: RoleId
  goal: string
  history: ChatMessage[]
  signal?: AbortSignal
  /** v0.9.4：Loom 上游结果注入（缺省时行为与 v0.9.3 完全一致） */
  context?: {
    loomNodeId?: string
    upstream?: { title: string; summary: string }[]
  }
}
```

调用链改动点仅三处：`SendMessageOptions`（`chatStore.ts:36-43`）加 `context` → `runAgentTask`（`:294`）透传 → `Orchestrator`（`src/harness/agent/Orchestrator.ts:63`，拼进 messages/system）与 `MockOrchestrator`（`src/harness/agent/MockOrchestrator.ts:24`，可以 reflect 文案展示）。`FallbackAgent` 原样透传无需改（`src/harness/agent/index.ts:21-36`）。

**输出侧**（原方案空缺）：节点输出定义为——

```text
node.output = 该节点 session 最后一条 assistant entry 的 content（截断 ~1200 字符）
            + trace 中 tool_result 的 summary 列表（截断 ~6 条）
```

节点成败判定沿用既有先例：`entry.error != null` 即 `error`（`focusStore.ts:75` 同口径）。

### 决策 3 · 画布删除简报节点必须防"复活"

**代码事实**：`ensureCardSession` 是"找不到才建"（`chatStore.ts:112-116`）。若 Loom 节点用同款幂等逻辑，用户"从画布移除"后，下次采纳同一张卡 / 重新打开画布时节点会重新出现。

**决策**：board 增加墓碑集合：

```ts
interface LoomBoard {
  // ...
  /** 用户显式"从画布移除"的 cardId：幂等建节点时跳过 */
  removedCardIds: string[]
}
```

`ensureLoomTaskNode(role, cardId, title)` 命中墓碑直接返回 `null`。画布节点菜单 v0.9.4 **只提供"从画布移除"**；"删除整个任务"（含 ChatSession）继续走侧栏既有入口，不在画布上暴露危险动作。

## 五、风险与对策

| 风险 | 对策 |
| --- | --- |
| LoomRunner 与 `streaming` 单飞互斥 → 执行卡死或状态竞争 | 执行前检查 `streaming`，占用则节点回 `queued` 等待；不做真并行（延续原方案） |
| 执行节点时 `activeId` 跳转，中栏聊天"跟着跑" | 批次前记录 `activeId`，批次后恢复；节点状态在画布表达 |
| 画布删除节点后"复活" | 墓碑集合 `removedCardIds`；移除动作与删除任务分离 |
| 节点位置高频写 localStorage 卡顿 | 拖动只写组件态，`pointerup` 提交 + 300ms debounce；沿用 v0.9.3 P2-A 先例 |
| 包体超限 | 先实测再定阈值；坚持零新依赖；画布代码如需可懒加载 `React.lazy` |
| 性能验收无法脚本化 | 改为耗时长任务计数口径；帧率做人工 Performance 面板复核 |
| 画布键盘操作与简报方向键守卫冲突 | 画布内键位（Enter / Delete / Ctrl+Z）只挂画布容器，不挂 window；复用 `shouldIgnoreDecisionKey` 判定思路 |
